# ADR-0005：环境就绪检查档及其权威边界

状态：接受
日期：2026-07-26

> 本仓库当前并存两套决策记录约定：`docs/adr/`（日期前缀，无状态字段，仅一个文件）与 `docs/decisions/`（编号前缀，含状态字段，被 handoff 必读清单直接引用）。`docs/agents/domain.md` 指向前者。本文件遵循后者，因为它是当前实际在用的一套。两套目录的合并不属于本次范围，留作独立决定。

## 背景

UI Test Harness 此前只有一个运行档位：真实验收。它要求真实 CodeArts 会话完成 Task 认领、确定性 MCP 调用、RunEvent 发布与浏览器验收，由 Authority 判定 Task 与 Run 均已完成。

这一档位的证明力最强，但它的可用性取决于一条很长的链：CodeArts 客户端可用、OAuth 会话有效、模型可达且有额度、MCP 审计目录在 server 启动前已绑定。历史证据显示，最频繁的失败恰恰落在这条链的外部依赖段，而不是被测对象或框架本身。同时它不自启动任何依赖：唯一一次完整跑通需要人工按顺序拉起 Relay、OpenChamber 生产服务与 CodeArts，再手工拼接会话关联参数。

结果是，「这套验收环境现在能不能用」这个问题，只能通过一次完整的真实验收来回答；而当它失败时，无法区分是环境没准备好，还是产品真的有问题。

## 决策

新增**环境就绪检查**档位，与真实验收并列，并固定三条边界。

**一、语义边界。** 环境就绪检查的通过，只断言依赖齐备、四个部件能起能关、被测 GUI 诊断干净、Authority 写入路径可用。它**不**断言产品行为正确。任何「端到端已验证」的结论只能来自真实验收。两档在命令名、输出与 Evidence 中必须显式区分，不得互相替代。

**二、被测边界。** 环境就绪检查启动**真实** CodeArts 并等待 TUI 就绪，只是不提交任务、不等待权威终态。不使用替身 PTY：客户端能否启动、TUI 能否渲染，正是该档位要回答的问题的主要组成部分，替换掉它会让该档位的通过失去意义。

**三、依赖归属边界。** 框架持有并常驻无凭据 loopback 依赖（Authority Relay 与 OpenChamber 生产服务），因为它们确定、可复用，且跨多次运行摊薄启动成本。框架**不**接管 CodeArts：它涉及 OAuth 会话与必须同独立 OpenCode 隔离的私有数据目录，自动化它等于代用户处置私有状态。CodeArts 只被预检，缺失时给出补救指引。

## 替代方案

- **只保留真实验收，把可用性问题交给文档**：不采用。它让最常见的失败（环境没准备好）与最需要区分的失败（产品有问题）共用同一个红色，且每次判断都要付完整真实验收的代价与外部额度。
- **就绪检查使用替身 PTY，完全不启动 CodeArts**：不采用。这样最快最稳，但它把历史上最易失效的一环从检查范围内移除，其绿色不足以支撑「环境可用」的结论。
- **框架同时接管 CodeArts 的启动与认证**：不采用。见依赖归属边界。
- **沿用 `smoke` 命名**：不采用。该词在本仓库已指 Provider 与平台 CLI 探针（`provider:smoke`、`douyin:host-smoke`），复用会使「smoke 过了」成为歧义陈述。

## 后果

- 日常判断环境可用性不再需要消耗外部模型额度或依赖 OAuth 有效性以外的条件。
- **新增一类可被误读的绿色。** 环境就绪检查通过而产品有缺陷是完全可能的正常状态。这一风险由命名、输出措辞与本 ADR 共同承担；任何把该档位结果当作验收结论的引用都属于误用。
- 环境就绪检查会在 Authority 中留下不会被完成的 Task。它们通过约定的 projectId 前缀可识别、可清理；本决策不为此给 Relay 增加删除语义。
- 被测 GUI 的诊断门被纳入就绪检查，意味着 OpenChamber 上游回归会使日常检查变红，即使本仓库未作改动。诊断结论必须指明责任方，避免误判为框架缺陷。
- 常驻依赖使运行之间存在共享状态。它由显式的启动与停止命令管理，不引入自动回收。

## 验收

1. 环境就绪检查与真实验收是两条独立命令，各自的输出与 Evidence 均标明所属档位。
2. 环境就绪检查在 CodeArts 未安装、未授权或无法就绪时失败，并指明该原因与补救方式，而不是报告为超时。
3. 环境就绪检查不调用外部媒体 Provider，不部署、发布、上传或提审。
4. 真实验收的既有门禁不因本次新增而放宽：Authority 终态、MCP Audit、浏览器诊断与超时门禁均保持原样。
5. 任一档位的依赖缺失都在运行开始前由预检报告，且报告发生在 Evidence 目录创建之后，使失败可追溯。
6. 常驻依赖停止后其占用的端口确实释放，重复启动与并发停止均收敛。
